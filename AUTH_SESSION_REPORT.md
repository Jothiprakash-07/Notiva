# Notiva authentication and session refactor

Completed locally on 13 October 2026. No commit or push. Earlier recurrence work and unrelated existing changes are preserved.

1. **Previous registration/login behavior.** Registration created a user and returned a seven-day JWT. Login used Notiva ID with legacy email fallback; JWT/tokenVersion was the only server authentication state. There was no refresh endpoint or device session collection.

2. **Previous automatic login.** The registration screen saved the returned token through AuthContext and navigated directly to tabs.

3. **New registration flow.** Registration creates the account only, returns no token, and creates no session record. The screen clears both password inputs, displays “Account created successfully”, and returns to Login. Existing fields, validation, ID suggestions, availability checks and organization verification remain. Passwords are never prefilled.

4. **New login flow.** Manual credentials plus installation metadata establish a session. Notiva ID and legacy email fallback remain. Wrong credentials never reveal device metadata. Concurrent submissions are guarded. Login and transfer requests have bounded timeouts. Splash, onboarding storage and existing account selection remain in place. Stored sessions restore local access while background validation/renewal runs; a network outage does not discard local access.

5. **Session model and timing.** A dedicated Session collection has one mutable slot per user: userId, random sessionId, installation/device metadata, tokenVersion, creation/last-seen/expiry timestamps, revocation fields, hashed refresh credentials and bounded transfer challenges. Access tokens last **15 minutes**. Refresh rotation extends a **30-day inactivity expiry**, so active users stay signed in without a daily login; 30 days without renewal requires login when online again. This implements the clarified secure-renewal preference while retaining finite session expiry. Last-seen writes are throttled to five minutes. There is no new periodic heartbeat.

6. **Device ID strategy.** A random UUID v4 comes from the already-installed Expo Modules Core UUID API. Native storage uses SecureStore; web uses the existing localStorage convention. Generation is shared across concurrent callers and survives restart. Device labels use Android/iOS/browser plus app version. No hardware identifiers or permissions are requested.

7. **Single-active-device enforcement.** Startup explicitly creates unique userId and sessionId indexes, plus an expiry TTL index; autoIndex remains disabled. A conditional update replaces the session UUID and credentials within the same document. Concurrent first logins use the unique user slot; concurrent transfers compare the old UUID and challenge, so only one wins. TTL deletion is cleanup only: authentication checks expiry itself. This does not require MongoDB transactions or a replica set.

8. **Conflict API/UI.** POST /api/auth/login returns 409 ACTIVE_SESSION_EXISTS after valid credentials when another installation is active. It returns safe metadata and a transfer proof, never an access token. The focused, scrollable modal offers Cancel and “Sign out other device & continue”. Cancel sends no takeover request and leaves the existing session active. The entered password is cleared when conflict appears.

9. **Replacement security.** POST /api/auth/replace-session requires a random 256-bit challenge, account ID and the intended installation ID. The challenge is hashed in storage, expires after five minutes, binds to the password tokenVersion and current session, and is consumed atomically by replacing the slot and clearing all pending challenges. At most five challenges are retained. Login/transfer/refresh use the existing per-process rate limiter. Refresh secrets are hashed; rotation has a one-minute retry window that reproduces the same replacement secret without storing plaintext. Revoked, expired, wrong-user and stale-version sessions cannot refresh.

10. **Old device.** Session-bound JWTs must match the current slot, tokenVersion and expiry. A replaced UUID receives SESSION_REVOKED. The shared authenticated transport attempts renewal where appropriate and clears auth when the server rejects the session. Existing protected routes return to the canonical entry/Login flow. Local reminder files and alarm schedules are not deleted.

11. **Logout.** AuthContext clears memory/account selection immediately and serializes deletion of the existing auth storage record. A separate bounded request revokes the current server slot. Refresh proof supports logout after access-token expiry, with bearer authentication as fallback. GET /api/auth/sessions and DELETE /api/auth/sessions/:sessionId expose/revoke only the authenticated user's own current session. Offline logout does not wait for the network; no unsafe cross-account revoke queue is created.

12. **Password reset/change.** Both increment tokenVersion and require normal login; neither creates an authenticated session. Session-aware users' older session records, refresh credentials and pending challenges are revoked. Revocation filters older tokenVersions so a legitimate concurrent login with the new password is not revoked. Middleware rejects the previous version even if the cleanup write fails. The frontend retains compatibility with an older server's replacement-token response, but the new server consistently requires login after password change.

13. **Offline revoked sessions.** Offline reminders, recurrence, alarms and queued edits remain local. On reconnect, failed session validation stops authenticated sync and clears auth. Pending data stays in its original account namespace until that account legitimately signs in again; another account cannot see it. Renewal responses arriving after logout/account switch cannot restore the previous session or replay work under another account.

14. **Profile screen.** Profile > Password & Security now links to Devices / Sessions. It shows current device, Active now, platform and last active, with retry and Sign out actions. The route is inside the existing protected stack. Text wraps in the existing responsive ProfilePage. Historical sessions are not retained or displayed: replacing the single slot invalidates the old UUID.

20. **Known limitations and rollout.**
    - Restart/deploy the backend before using the updated client; startup must successfully create the indexes. No production deployment or live database migration was performed here. Configure a production HTTPS API URL; the existing LAN HTTP development configuration is unchanged.
    - Existing unbound legacy JWTs remain usable until their original expiry or the user's first session-aware login, which sets sessionEnforced and invalidates them. Legacy devices cannot be identified retroactively; that first login cannot show metadata for those old tokens. All newly issued tokens require a session UUID. Older clients without installation metadata must update before signing in again.
    - Thirty days without renewal requires normal login on reconnect. Local offline use is not blocked by an unavailable server.
    - Offline logout cannot immediately revoke the unreachable server slot; it expires or is replaced after a subsequent credential-based login. Unsynced changes remain local until legitimate re-login.
    - A refresh response lost for longer than the one-minute retry window, or persistent storage failure after rotation, can require normal login. This bounds reuse of an older secret.
    - Native secrets use SecureStore; web retains localStorage's existing security properties. iOS Keychain storage can survive reinstall. Labels are generic platform names rather than hardware model names.
    - Backend concurrency tests use conditional model doubles and unique-index contract checks, not a live MongoDB race test. Frontend checks use native-control mocks; a two-physical-device auth walkthrough and manual visual checks were not performed. Native scheduler regression tests use the existing compiled classes. No claim of a new APK or live-device authentication test is made.
    - Rate limiting is per backend process, matching the existing project strategy; a multi-instance deployment should provide shared edge/server rate limiting.

21. **Native changes.** None for this auth task. No new dependencies. Existing Kotlin changes from the earlier recurrence task remain untouched.
