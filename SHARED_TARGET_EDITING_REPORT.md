# Shared item target editing

Implemented for shared Reminder, Task and Event. Personal item code and native alarm code were not changed in this task. No commit or push was performed.

1. **Previous limitation and API.** Audience expansion previously happened only at creation; edits rejected `targets`. PATCH now accepts optional `targets` in the existing canonical format (`targetType: organization|team|user`, `targetId` for team/user) alongside `expectedRevision`. Organization, one/multiple teams, selected employees and mixed team/user definitions are supported. Supplying targets explicitly takes a fresh snapshot of the final definitions. Omitting targets leaves the existing snapshot untouched.

2. **Authorization.** Owner and Admin with `edit_shared_items` can edit audiences. Creation permission is independent. A Member creator must still be an active organization member, have employee sharing enabled, and manage an employee-only item; their final targets must remain selected employees. Ordinary recipients and unauthorized Admins are denied. Creator departure does not remove Owner/authorized Admin management. Current ownership/membership permissions are checked transactionally.

3. **Recipient difference algorithm.** The existing organization transaction first checks revision and expands every validated final target against active organization membership and active teams. A map keyed by user deduplicates all coverage sources. It then compares this final audience with existing unique `(item,user)` recipient rows: unchanged, added, reactivated and removed. Responses include counts for those groups. Overlap across Sales/Design or an explicit user never creates duplicate recipients. Active target rows retain their IDs; removed definitions become inactive audit rows and can be reused later. Historical target IDs are not deleted.

4. **Added recipients.** New rows start active and pending, record their source target IDs and available master revision, and use normal one-off eligibility or a recurring grant boundary. They receive no copied/backfilled completion or missed-occurrence rows. Expansion excludes left/removed/inactive organization members even if a stale active team link remains.

5. **Removed recipients.** Rows become `accessStatus: revoked` with `revokedAt`, `revokedByUserId` and `removalReason: target_change`. Status, response timestamps, occurrence history, original creation metadata and the logical row remain. Ordinary recipient reads/actions stop; authorized managers retain management visibility. Devices clear cached recipient content, pending occurrence intents and native schedules once removal is observed. Organization leave/removal uses the separate `organization_access` reason.

6. **Re-add.** An explicit authorized target save may reactivate an existing row if the user is currently an active organization member. It preserves that row's ID, creation time and response/history evidence, updates source coverage and grants current/future recurrence eligibility anew. Active members who previously left/rejoined can receive a deliberate new grant through this explicit snapshot edit; rejoining alone still grants nothing. No duplicate row or historical backfill is created.

7. **Completion preservation.** Unchanged recipients keep acknowledgements/completions/history. A recurring globally completed occurrence is never reopened by audience changes. A completed or cancelled one-off item cannot be edited. Removing the last pending recipient from an active individual one-off task completes the remaining all-completed audience, with exactly one master revision increment for the edit. Other historical completion records are not rewritten.

8. **Recurring series.** Target-only changes increment `serverRevision` once without incrementing `scheduleRevision` or changing recurrence effective time. Existing occurrence keys/history stay valid. Active series may change audience even when their current occurrence is globally completed; new recipients start at the next eligible slot. Current individual completion aggregation/counts exclude recipients whose grant starts later or excludes that occurrence, so future-only additions do not block today's eligible audience from finishing. Management detail exposes total active recipient count separately from the current eligible summary.

9. **Exact activation rule.** At the server update instant, a new/re-added recipient receives a current Reminder/Task only when its scheduled instant is still in the future. A recurring Event also qualifies while ongoing, including its existing end-time boundary. An expired or globally completed current slot is excluded and the next valid recurrence is scheduled. A grant timestamp plus an optional excluded current key enforces this on reads, offline derivation, virtual history and server actions; no old response is invented. For an ongoing Event the boundary includes its start. The boundary is based on the grant, not a stored future alarm timestamp, so a later schedule edit moving the next occurrence earlier does not incorrectly postpone access. Existing unchanged recipients retain their original eligibility and overdue/missed state.

10. **Alarms/native re-arm.** Detail/inbox reconciliation registers alarms only for the signed-in active recipient. Addition schedules its eligible alarm/pre-alert; removal cancels the stable shared series handle, clears persisted native re-arm metadata through the existing cancellation path and removes cached series state. The target-edit ACK includes the editor's authoritative recipient/alarm state, so self-removal clears alarms even if every follow-up read goes offline. Unchanged alarm fingerprints reuse their schedule. Manager edits never schedule other people's alarms locally. Other organizations/accounts remain isolated. A disconnected device learns remote removal/cancellation on its next successful sync; it cannot cancel based on information it has not received. The existing native cancellation test confirms cleared metadata cannot resurrect an alarm.

11. **Frontend edit UI.** The existing picker now loads current team/user selections in Edit, supports organization/team/employee/mixed modes according to edit permissions, and offers removal of unavailable historical teams/employees without exposing hidden profiles. It shows “Changing recipients affects future alerts.” and the requested recurring current/future helper. Target-only saves omit unchanged schedule/rule fields. After save, authoritative detail and workspace refresh update targets, counts, current status and list caches. A 409 reloads authoritative content and target selections. An exact recipient-difference confirmation is skipped because the client does not have complete per-team coverage; it does not guess overlap counts.

12. **Offline edits.** Target changes require a live server response. Cached/offline forms disable save and display “You're offline. Connect to update recipients.” Network failure during a target save shows the same message. Target changes never enter the occurrence acknowledgement/completion queue and are never presented as synced optimistically. Existing offline occurrence responses continue to work within their grant boundary.

13. **Cross-organization protection.** Every final team/user target must be active in the item's organization. Archived teams, foreign teams/users, mixed valid/foreign input and inactive users fail generically before writes. An item ID in another organization returns not found. Target rows, recipients and content are committed together; an injected recipient-write failure verifies rollback of all of them.

14. **Concurrency.** Target edits use `expectedRevision`; stale input returns HTTP 409 with `ITEM_REVISION_CONFLICT`. Two simultaneous edits at the same revision produce exactly one success and one conflict, and the final audience equals the winner only. No mixed or partial recipient set persists. Existing content-only conflict behavior remains compatible.

15. **Validation.** Full backend suite: **260 passed** (organization/team/auth/session/shared/recurrence/target tests), using real disposable MongoDB replica sets with sequential test execution. Target coverage includes permissions, mixed/overlapping coverage, removal/re-add/history, active organization expansion, stale team links, archived/foreign targets, rollback, conflicts/races, inactive item rules and recurring timing. Frontend: **8 target service checks, 30 shared service checks, 22 rendered UI checks and 15 shared recurrence checks passed**. Personal recurrence, item sync/session renewal, native alarms and pre-alert JS regressions passed. Existing compiled Kotlin cancellation/fire/group/restore checks plus **1,320 JS/Kotlin parity cases passed**. TypeScript and web export passed. Lint: zero errors and five pre-existing warnings.

    This machine intermittently fell below MongoDB's default 500 MB index-build disk reserve. Generated Android intermediate caches were cleared while retaining the APK/compiled Kotlin classes. Disposable test fixtures now accept `NOTIVA_TEST_INDEX_DISK_MB` (default unchanged at 500, minimum 100); the final run used 100 MB. This only configures launched test processes, never an existing/production database. The parameter is documented in the [MongoDB 8.0 server parameter reference](https://www.mongodb.com/docs/v8.0/reference/parameters/#mongodb-parameter-param.indexBuildMinAvailableDiskSpaceMB).

17. **Limits.** Snapshot targeting remains fixed between explicit audience edits; later organization/team joiners are not added automatically. A provided final target set re-expands current membership, so a changed snapshot can remove an old recipient no longer covered by any final target. Archived teams may remain in historical metadata, but cannot be accepted in a submitted final target set. No offline target queue, guessed recipient-count preview, dynamic targeting, advanced analytics or new physical validation was added. Remote changes require recipient-device sync. Access metadata records current grant/revocation state; this is not a separate unbounded access-change ledger.
