# Stale edit and delete protection — 17 October 2026

1. **Previous concurrency behavior.** MongoDB `revision` starts at 1; successful mutations increment it, and the frontend stores it as `serverRevision`. PATCH supported optional If-Match. Sync fetched the latest server revision before PATCH, automatically merged compatible series, and could retry a racing series write. DELETE was unconditional. Successful acknowledgement stored revision/server timestamp; transient failures used backoff.
2. **Root risk.** A stale offline snapshot could be submitted against a freshly fetched revision rather than its original base. Deletes could remove newer data. Single-active-session enforcement prevents revoked credentials from writing, but does not make old local edits current after legitimate re-login.
3. **Backend contract.** PATCH and DELETE require a positive safe-integer `expectedRevision`. Existing unquoted integer If-Match is also supported, but cannot disagree with the body. Missing/invalid revision returns 400. Create semantics and unique owner/clientItemId indexing are unchanged. Wire/storage field remains `revision`; frontend maps it to `serverRevision`.
4. **Atomic revision check.** One findOneAndUpdate filters ownerUserId, clientItemId, deletedAt:null and revision:expectedRevision; update fields/deletion and `$inc: { revision: 1 }` execute together. No read-then-write mutation. An owner-scoped read occurs only after a failed conditional operation to distinguish active mismatch from missing/deleted data.
5. **409 response.** `{ success:false, code:'ITEM_REVISION_CONFLICT', message:'This item has changed since your last sync.', serverItem:<public authoritative item> }`. Another owner's item produces 404 without serverItem. An already soft-deleted item accepts a delete retry without another revision increment; archived/missing deletion remains compatible with the existing 404 acknowledgement/feed path.
6. **Frontend handling.** Queue mutations retain the base expectedRevision instead of rebasing on a fresh GET. HTTP 409 records local syncStatus conflict and device-only metadata: expectedRevision, serverRevision, detectedAt, whitelisted serverItem. Local edits remain intact. Recurring masters use exactly the same rule; no automatic merge, server overwrite, local overwrite or revision bump on conflict. No resolution UI was added.
7. **Queue behavior.** Conflicted entries retain payload, error:conflict and server copy, and are skipped on future automatic runs, including after restart or further local edits. Other entries continue. Pending deletes retain their local payload snapshot and an unsynced conflicted local tombstone; no server tombstone is created by a rejected delete. Successful earlier create/PATCH acknowledgement can advance a dependent edit/delete made during that same in-flight request; this is acknowledgement of an accepted write, never conflict rebasing. Legacy updates can recover their base only from the stored local item. Legacy deletes with no recoverable base remain blocked as invalid_or_missing_item rather than borrowing a newer server revision.
8. **Update conflict tests.** PASS: matching 10->11; stale update rejected; server/local copies retained; metadata persists; retry blocked across restart/further edits; unrelated item sync; cross-account isolation; create retry deduplication; edits during successful in-flight writes. Existing item-sync suite passes all 38 checks; dedicated conflict suite passes 10 scenario groups.
9. **Delete conflict tests.** PASS: stale 5 vs 6 rejected with no server mutation/deletion; local deletion snapshot retained; matching delete increments once; repeat delete does not increment; unknown legacy delete base blocked. Authoritative remote deletion still clears stale pending updates and prevents resurrection.
10. **Race tests.** PASS in repository-backed HTTP tests and real MongoDB: two requests with expectedRevision 4 yielded [200,409], with final revision 5. Mixed update/delete race also covered in HTTP tests. Backend repository double models the conditional filter at commit time; live MongoDB independently verified the database behavior.

17. **Remaining limitations.** Resolution is intentionally deferred: persisted conflict evidence is exposed for future Keep mine/Use server/manual-merge UI, and unresolved operations remain blocked. Local pending deletion remains hidden under the existing tombstone design. A lost successful PATCH response can conservatively become a conflict on retry; no unsafe automatic rebase is attempted. Very old pending deletes without a base require explicit future resolution. Clients that omit both expectedRevision and If-Match must update.
