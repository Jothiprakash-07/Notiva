# Notiva shared recurrence foundation

Shared audience edits and new-recipient recurrence eligibility are documented in the [target editing report](SHARED_TARGET_EDITING_REPORT.md), superseding earlier target-edit deferrals.

The Android stopped-app re-arm limitation and native/APK conclusions below are superseded by [Shared recurring alarm re-arm reliability](SHARED_RECURRING_ALARM_REARM_REPORT.md). The follow-up adds native recurring metadata and receiver re-arming and requires the rebuilt APK.

Implemented Daily, Weekly (selected weekdays), Weekdays, Monthly and Yearly for shared Reminder, Task and Event. No Git commit or push was performed. Physical device validation remains deferred.

1. **Recurrence model.** One `OrganizationItem` master with `recurrence: { repeat, timeZone, weeklyDays?, effectiveFrom }`, existing `schedule.startAt/endAt/alertBefore`, and `scheduleRevision`. `none` preserves one-off behavior. Timezone is an IANA identifier captured at creation; device timezone changes do not move the series. No interval/end-date feature was added because the personal format does not support it.

2. **Occurrence state.** Existing fixed recipient documents hold compact `occurrenceHistory` arrays, bounded to the latest 366 actual responses by scheduled time. The master holds at most 366 global task completion results. Each result includes occurrence key, scheduled time, status and response timestamps/actor as applicable. Embedded state keeps response and collective aggregation inside the existing serialized organization transaction. No future item, target, recipient or occurrence documents are generated. Missed/overdue history is derived virtually for the latest 30 dates; actual responses and global completion results alone are persisted.

3. **Occurrence identity and canonical calendar.** Keys are `scheduleRevision|YYYY-MM-DDTHH:mm` in the series timezone. Item, organization and recipient/account namespace them for alarms. The shared adapter uses a reproducible generated bundle of the unchanged personal `dailyRecurrence.ts`, `weeklyRecurrence.ts` and `itemStatus.ts`; it adapts their local Date operations to IANA wall time. Run `node scripts/build-shared-calendar.cjs --check` to verify the bundle against source, or regenerate after intentional personal-calendar updates. Invalid monthly dates are skipped, February 29 waits for a leap year, DST gaps roll forward and folds choose the earlier instant. The current slot activates only at midnight on its valid series-local date; the next alarm can be registered earlier without creating a future actionable card.

4. **Individual task completion.** Each recipient completes the exact occurrence independently. All active recipients completing that key records global completion for that occurrence. The master stays active; a later valid date starts pending. Revoked recipients are excluded from aggregation.

5. **Collective ANY.** The first accepted completion records a global result with completion actor/time. Concurrent responses serialize through the organization transaction and produce one logical global result. Later retries are idempotent. Tomorrow remains a fresh occurrence. ALL/quorum remain deferred.

6. **Reminder.** Acknowledge/complete applies to the recipient's occurrence. Acknowledgement suppresses that occurrence's future alarm; completion can follow acknowledgement. Passing an unresolved due time derives Missed without completing the series.

7. **Task.** Unresolved past due time derives Overdue. No automatic completion occurs; subsequent recurrence dates activate independently.

8. **Event.** Each date derives Upcoming, Ongoing and Completed using the occurrence start and the original event duration. Acknowledgement is occurrence scoped. No attendance feature was introduced.

9. **Alarms.** The existing bridge receives a one-off temporary notification payload for the next unresolved future occurrence. Its deterministic ID contains organization, item, occurrence and existing account namespace. Shared payloads never enter personal item storage. Reconciliation removes replaced schedules before registering the new one and persists a recovery journal. The existing bridge retains same-minute grouping behavior; each occurrence has one logical native entry. Main alarm delivery/grouping still needs device validation.

10. **Pre-alert.** The existing scheduler pairs the configured pre-alert with that same occurrence entry. Reconciliation/restart reuses stable IDs, completion cancels the old pair and schedules the next eligible pair. Expired pre-alert handling remains the existing bridge's behavior.

11. **Restart/restore.** Rules and bounded histories load from account/organization cache, derive the current slot and reconcile the one next alarm. A separate active-series cache avoids losing series through the recent inbox display limit. Foreground, resume, focus and periodic refresh reconcile schedules. A local timezone-midnight timer updates views and alarms without waiting for a successful network request. Relogin/server restore uses authoritative fixed recipients/history.

12. **Offline behavior.** Synced rules/history support local current-slot derivation. Only occurrence acknowledgement/completion gets a small durable queue (100 unique intents per organization). Exact key, action and expected master revision are preserved; the UI explicitly says pending sync. Reconnect replays the original date, never today's replacement. Network/5xx errors retain intent; validation/access/revision errors become visible conflicts that can be dismissed after review. Pending overlays do not mutate authoritative history. Replay accepts a valid past slot up to 366 local calendar days old, with already-retained successful responses remaining idempotent. Revocation removes cached series/actions/alarms once discovered. Offline devices cannot discover remote changes before reconnecting.

13. **Edits.** Existing permissions and `expectedRevision` apply. Title-only edits preserve schedule generation. A schedule or recurrence change increments `scheduleRevision` once, increments master revision, and applies the new rule from `max(server update instant, updated schedule.startAt)`. A same-day slot whose scheduled instant is already earlier than that point is excluded. Existing history keeps its original keys and timestamps. Old-generation queued actions conflict rather than migrating to a new rule. Targets and completion mode remain fixed. Cancelled series cannot be edited.

14. **Cancellation.** Idempotently changes series lifecycle to cancelled, disables all future occurrence/alarm derivation and preserves recipient/global history. Completing an occurrence never cancels or permanently completes a recurring master.

15. **Snapshot recipients.** Creation captures a fixed recipient set. Later team joiners do not join this series. A recipient leaving its targeted team continues this existing recurring series while still an active organization member. Organization leave/removal revokes future access/alarms permanently for that receipt, including after rejoin, while retaining audit history. Existing non-recurring team eligibility rules remain unchanged.

18. **Limits/deferred work.** Only one next alarm is registered. The already-registered alarm can fire offline with the app stopped, but another occurrence requires the JS runtime or a subsequent reopen/resume to register it; indefinite recurrence while the app stays terminated is not implemented. Manager counts are current server snapshots; while offline, other devices' responses cannot be known. The minimal manager history reports persisted global completion results, not historical per-recipient analytics. Old unresolved slots are a recent virtual view, not an unlimited ledger. Target edits, dynamic recipients, advanced analytics, ALL/quorum, and physical device validation remain deferred. Web export verifies bundling, not native alarm delivery.

19. **Native changed? No.** No Kotlin/native alarm files changed for this recurrence work; the existing bridge is used.

20. **APK rebuild required? No.** Native rebuild venam — backend restart + dev-client reload pothum. Physical alarm, pre-alert, grouping and restore validation should run on the existing compatible dev client at the planned final validation stage.
